## 4. Target architecture

```
 Ihor's Claude Code (CEO office) ──mwc CLI / @mwc/mcp (mwc_pk_… key)───────┐
 Browser (React UI, Clerk sign-in) ──REST + SSE (Last-Event-ID)────────────┤
                                                                            ▼
                 ┌────────────────── apps/server (Hono, :9950) ──────────────────┐
                 │ authn: Clerk JWT | api key | run token → Actor; tenant(db,cid)│
                 │ domain: org, tasks, runs (state machine), attention, inbox    │
                 │ jobs: identity outbox/reconcile, scheduler, lease reaper      │
                 │ runner hub: WSS /api/runner/ws (hello, lease, offers, acks)   │
                 └──────▲──────────────────────▲──────────────────────▲──────────┘
                        │ Drizzle / LISTEN-NOTIFY                     │ outbound WSS only
                  Postgres :9952                     ┌────────────────┼────────────────┐
                  (migrate = one-shot step)   mw-runner (Mac,   mw-runner (devbox,   runner-local
                                               launchd)         systemd --user)      (compose / k8s, PID 1)
                                                 │ state dir, journal, unix socket, health :9953
                                                 ├─ detached `claude -p … --resume` per run (stdin fifo, stdout journal)
                                                 └─ per-run stdio MCP shim → runner: ask_user, permission,
                                                    report_blocked, submit_for_review, post_message, read_task
```

- The server never SSHes, never spawns agent processes, never holds a Docker socket. Runners dial out, keep a lease by heartbeat, own their child processes, journal events to disk and resync after any disconnect. A server restart drops sockets only; a runner restart re-attaches to its detached harness processes.
- Secrets: Clerk keys, the credentials master key and the run-token signing key live in the server env. The runner key lives on the machine (`~/.config/mwc/runner.json`, 0600). Claude logins on the Mac/devbox stay in that agent's `CLAUDE_CONFIG_DIR` on the machine (never in the server). Setup-tokens, API keys, gateway headers and sign-ins for container runners are encrypted in `credentials` and delivered per run over the WSS into the process env (never to disk). Run tokens are short-lived JWTs scoped to one run.
- Messages from another agent or from the CEO chat are chat input only; they can never resolve a permission or an approval (Claude Code's own cross-session rule).

## 6. Data model v0 (Postgres; uuid v7 ids; `created_at`/`updated_at`)

Conventions: every tenant table has `company_id` and `UNIQUE(company_id, id)`; child FKs are composite `(company_id, parent_id)`, so cross-tenant references are impossible at the DB level. A table with one row per company (`company_logos`) has `company_id` as its primary key instead, and no `id`; one with one row per principal (`org_positions`) has `(company_id, principal_id)`. Enums are CHECK constraints mirrored by zod enums in `@mwc/shared`.

**Global (S1):** `users` (primary_email, display_name, status) · `user_identities` (provider, issuer, subject; UNIQUE(issuer, subject): identity is issuer+subject, never email) · `identity_events` (webhook/SCIM inbox; UNIQUE(provider, external_event_id); status pending|processed|failed; type a normalized event type or `ignored`, S1.8) · `identity_outbox` (local-first provider ops create_org|invite|revoke_invite|update_role|remove_member|delete_org; idempotency_key; retries) · `companies` (slug, name, status provisioning|active|suspended|deleted, identity_provider, identity_org_id UNIQUE, settings) · `identity_marks`, `identity_parked_events` (the projector's ordering marks and parked events, S1.3).

**Tenant (S1):** `principals` (kind person|agent; the single id space every actor/assignee FK points to) · `memberships` (principal_id, user_id, role owner|admin|member|viewer, status invited|active|suspended|removed, external_membership_id; UNIQUE(company_id, user_id); ≥ 1 active owner) · `invitations` (email_normalized, role, status, external_invitation_id, expires_at; one pending per email) · `api_keys` (principal_id, kind personal|runner|scim, machine_id, prefix, sha256 hash, scopes, expires_at, revoked_at) · `audit_log` (one row per changed field: entity, action, field, old, new, actor, request_id) · `company_logos` (added 2026-11-05: one per company, `company_id` the primary key and cascading with the company row; content_type png|jpeg|webp, bytes, size 1..1048576, sha256, updated_by_principal_id).

**Tenant (S2, built in S2.1, migration `0005_org`):** `agents` (principal_id, one agent per principal, whose kind `agent` the org service checks; name 1–80; slug kebab like company slugs, UNIQUE(company_id, slug); role_title 1–80; status active|paused|archived default active; harness claude_code|codex default claude_code; model; effort low|medium|high|xhigh|max default high; instructions default empty; instructions_rev ≥ 1 default 1; max_concurrent_runs 1–8 default 1; face 0–41 default 0, the web's drawn face; settings) · `org_positions` (one per principal: `(company_id, principal_id)` is its primary key and it has no `id`; reports_to_principal_id nullable, never the principal itself; title at most 80, nullable; invariants: no cycles, agents never root, an agent's chain reaches a person, agents never manage people, held by the org rules and service (S2.2, S2.3), not by SQL). A company's creation places its owner at the root; `0005_org` placed the existing active memberships (owners at the root, the others under the company's earliest active owner). *Built in S2.3* (`apps/server/src/modules/org/`): `GET/POST /agents`, `GET/PATCH /agents/:agentId` (archive moves the agent's reports up and takes it off the chart; no hard delete), `PUT /org/positions/:principalId` (moves for admins, titles for admins and for oneself) and `GET /org/chart` (`{nodes, tree}`), under `/api/companies/:companyId/`; every change runs under the company row's lock and refuses, with the rules' code as a 422, a chart that would break an invariant it did not break before; the limits are `@mwc/shared/org`, which the CHECKs read too (docs/roadmap.md, S2.3). *Built in S2.4* (`apps/server/src/modules/org/service/lifecycle.ts`): a membership that turns active, on any path, places its person under its invitation's inviter when that is a person on the chart, else under the earliest active owner, else at the top (a person with a position keeps it); one that stops being active (removed, suspended) moves the person's direct reports up and removes their position; both in the membership's own transaction under the company row's lock, with `org_position` audit rows. A removal is never refused for the chart: a flaw it leaves (an agent at the top when no other owner is left) is logged. Role changes and a company's soft delete move nobody (docs/roadmap.md, S2.4).

**Tenant (S3–S6):** `machines` (name, kind laptop|vm|container, os, arch, unix_user, claude_version, runner_version, slots, status online|offline|draining, last_seen_at) · `enrollment_tokens` (sha256, expires_at, used_at) · `runner_sessions` (machine_id, connected_at, disconnected_at, protocol, remote_ip) · `runner_releases` (version, url, sha256, sig, min_runner_version) · `agent_placements` (agent_id, machine_id, home, config_dir, worktree_root, permission_policy ask|bypass, unix_user, is_default) · `tasks` (per-company number, title, body, status backlog|todo|in_progress|in_review|blocked|done|cancelled, assignee_principal_id, created_by_principal_id, parent_task_id) · `messages` (task_id, author_principal_id, kind user|agent|system, body, attachments) · `task_sessions` (task_id, agent_id, machine_id, folder, harness, session_id, state active|superseded) · `runs` (task_id, agent_id, machine_id, placement_id, session_id, state queued|offered|starting|running|lost|completed|failed|stopped, waiting_on null|permission|question, lease_expires_at, started_at, finished_at, exit_code, error, cost_usd, usage, last_seq; partial UNIQUE one live run per task) · `run_events` (id bigserial, run_id, seq, kind, data, at; UNIQUE(run_id, seq)) · `run_inputs` (run_id nullable, task_id, kind message|answer, payload, delivered_at, acked_at) · `attention_items` (kind question|permission|blocked|review|failed|done, state open|answered|dismissed|expired, task_id, run_id, to_principal_id = nearest person up, wait_mode live|next_turn, prompt/options jsonb, answer jsonb, answered_by, expires_at, tool_use_id). A run's use of a credential is recorded in `credential_uses` (below; the plan's `credential_deliveries`).

**Personal (S3, built in S3.1, migration `0007_credentials`; docs/subscriptions.md):** a person's own rows, which belong to no company: `owner_user_id` (a user) and no `company_id`. `credentials` (kind claude_oauth|claude_setup_token|codex_oauth|anthropic_api_key|openai_api_key|gateway; label 1–80; account_email; account_meta, a JSON object of non-secret details such as plan, organization, scopes, a gateway's base URL; status active|needs_sign_in|revoked default active; the sealed secret: key_version ≥ 1, iv 12 bytes, auth_tag 16 bytes, ciphertext; last_used_at) · `credential_uses` (credential_id with no foreign key, so the record outlives the credential; owner_user_id; purpose 1–80; at). The secret is AES-256-GCM under the master key of `key_version` with a random IV and the AAD `credential|<id>|<owner_user_id>|<kind>` (the plan said `company|owner|provider`: subscriptions are personal), sealed and opened only by the server (`apps/server/src/platform/secrets/keyring.ts`), so a row copied to another id, owner or kind does not open. Code reaches these tables only through `owned(db, userId)` of `@mwc/db` (the personal layer: every statement scoped to `owner_user_id`, inserts stamped, audit rows with no company), never raw access. *Built in S3.1* (`apps/server/src/modules/credentials/`): `GET`/`POST /api/me/subscriptions`, `PATCH`/`DELETE /api/me/subscriptions/:credentialId` (section 7), and the internal `credentialSecrets(deps)`: `storeCredential` (seal and save, with the `create` audit rows) and `useCredentialSecret(credentialId, ownerUserId, purpose)` (open, check against the kind's shape, record the use, move `last_used_at`; a revoked one is refused). *Built in S3.4* (migration `0008_access_profiles`): `access_profiles` (personal: owner_user_id, name 1–80 unique per owner, claude_credential_id, openai_credential_id, gateway_credential_id, each a key to `credentials` with `on delete set null`; the slots' kinds and the owner of their credentials are the credentials module's rules, not SQL), reached by its owner through `owned()` and from a company through `@mwc/db`'s bridges (`ownersOf(t, table, ids)`, then the owner's layer on the tenant's connection, `ownedIn(t, userId)`; `o.tenant(companyId)` the other way), so one transaction spans both layers without raw access. Two tenant columns point at it with `on delete set null`: `agents.profile_id` (the profile an agent's runs use, given by its owner as an admin or owner of the company) and `memberships.default_profile_id` (the person's default for the agents they hire there); both are single-column keys, as a personal row has no company. `/api/me/access-profiles`, `profileId` on the agent routes and `PUT /api/companies/:companyId/me/default-profile` are docs/subscriptions.md's "Access profiles"; a membership that stops being active takes its person's profiles off the company's agents in the org chart's lifecycle transaction.

Tenant-scoping rule in code: `tenant(db, companyId): TenantDb` is the only way route code reaches tenant tables (`scoped(table)` injects `eq(table.companyId, companyId)`); the raw handle `@mwc/db/system` is import-restricted (Biome `noRestrictedImports`) to migrations, the webhook inbox, the identity store, the runner hub and jobs (built in S1.3: server modules may not import it, except the identity module's repo; `docs/structure.md`, "The tenant layer"). Routes get `c.var.tenant` only after `requireMembership(role)` (built in S1.4: our `memberships` through `tenant()`, 404 for a missing or deleted company and a non-member alike, 403 below the role; `docs/structure.md`, "The server"). No RLS in v0 (one DB role; composite FKs + lint rule + the generated cross-tenant fuzz test give the guarantee); adding `SET LOCAL app.company_id` + policies later is mechanical.

## 7. Identity flow (Clerk now, other IdPs later)

- **Sign-in:** web uses `@clerk/react`; API calls carry `Authorization: Bearer <session token>`. Server `authn()` verifies with `@clerk/backend` `verifyToken` (JWKS or `CLERK_JWT_KEY`, issuer, `authorizedParties=[WEB_ORIGIN]`, 5 s skew). Claims used: `iss`+`sub` (identity key), `sid`, `azp`, `exp/nbf`, `sts` (reject `pending` except on `/api/me`); Clerk's `o.id`/`o.rol` are hints only. Authorization never trusts the org claim: routes are `/api/companies/:companyId/...` and `requireMembership()` reads our `memberships`. First sight of an `(iss, sub)` runs reconcile-on-sign-in (upsert user; project memberships of companies whose `identity_org_id` matches). *Built in S1.4* (`apps/server/src/platform/auth/`): the provider verifies against `MWC_WEB_ORIGIN` and the issuer is checked once more; a pending session is 403 `session_pending`; an `(iss, sub)` with no link yet has no user, so company routes answer 404 until `GET /api/me` links it; reconcile also runs once per new session id (`sid`) of a linked person, so an invitation accepted by someone already known is picked up at their next sign-in; `MWC_IDENTITY=none` (no Clerk keys, as in the prod-like compose stack) keeps health and the UI up and answers 503 `identity_not_configured` behind `authn()`.
- **Create company:** one transaction inserts company(provisioning) + person principal + owner membership + root position + outbox `create_org`; the outbox worker calls Clerk `createOrganization({privateMetadata:{mwc_company_id}})`; retries find the org by metadata (as in v1)   ; then the company turns active. Policy `MWC_COMPANY_CREATION=any|allowlist|none`. *Built in S1.5* (`apps/server/src/modules/companies/`): the transaction is `withNewCompany` of `@mwc/db` (company, principal, owner membership, outbox row, audit rows; the root position comes with `org_positions` in S2); only a person signed in with a session and linked here creates (not an API key); `MWC_COMPANY_CREATION` defaults to `any`, and to `allowlist` with `MWC_COMPANY_CREATORS` (emails) in production; the `create_org` handler finds by metadata before creating, so a retry after a lost answer makes no second organization, and sends no slug (company slugs are ours; Clerk's organization slugs may stay off, S1.2 fix of 2026-11-04); `GET /api/companies` lists exactly what `GET /api/me` lists; rename and slug change (admin) and soft delete (owner, name typed again, outbox `delete_org`) are audited per field; the outbox rows are recorded by `platform/jobs/outbox.ts` (backoff 30 s doubling to 1 h or Retry-After, failed after 12 tries) and run by the jobs loop from S1.10.
- **Company logos:** *added 2026-11-05 on Ihor's request* (for "Add company logo" on the create-company page), ahead of the plan's "no photo uploads in v0" (section 17), in `apps/server/src/modules/companies/` (`routes/logo.ts`, `service/logo.ts`, `repo/logo.ts`). `PUT /api/companies/:companyId/logo` (admin and above) takes a multipart form with one field `file` (the typed client's `$put({ param, form: { file } })`): a body limit runs before parsing (1 MB and 16 KB of multipart framing; over it, or a file over 1,048,576 bytes, is 413 `logo_too_large`), an empty file is 400 `logo_empty`, and the type is told from the first bytes only (PNG, JPEG, WebP; anything else, SVG and GIF included, is 415 `logo_type_unsupported`, whatever the declared type or name). It replaces any logo, under the company's lock, and answers `200 {logo: {version, contentType, size, updatedAt}}`, `version` being the first 16 hex characters of the SHA-256 (`@mwc/shared/logos`). `GET .../logo` (any active member, viewers included) sends the bytes with the stored `Content-Type`, `ETag: "<sha256>"`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'`, `Content-Disposition: inline`; a matching `If-None-Match` is a 304; `?v=` equal to the current version gives `Cache-Control: private, max-age=31536000, immutable`, otherwise `private, no-cache`; no logo is 404 `logo_not_found`. `DELETE .../logo` (admin and above) is a 204, also when there was none. Non-members get the usual 404 and lower roles 403; API keys and session tokens both work. Company responses (`GET /api/companies/:companyId`, the list, `POST` and `PATCH`) and each membership of `GET /api/me` carry `logo: {version} | null`, read from `sha256` alone (a left join in the lists), never the bytes. Each set, replacement or removal writes the company's per-field audit row (field `logo`, old and new the SHA-256 or null, the member, the request id). The image lives in Postgres (`company_logos`); a soft-deleted company keeps its row, a deleted company row takes it along. Logos stay local: syncing them to the Clerk organization's logo is a possible later step, not done.
- **User profiles:** *added 2026-11-05 on Ihor's request.* A person's first and last name and photo live at the identity provider (Clerk's `first_name`, `last_name`, `image_url` with `has_image`), set with clerk-js from the web's `/onboarding` (asked before any other page while the name is missing: right after sign-up) and `/profile`, and copied into `users` by every sync path (the `user.updated` webhook, the reconcile on sign-in, `POST /api/me/reconcile`, which the web calls right after a save). `users.display_name` is the first and last name, trimmed, or null (never the email or the username; migration `0006` cleared the email stand-ins stored before), and `image_url` is the photo or null (Clerk's generated default image is not one). `GET /api/me`, the member list, API key owners and the org chart's person nodes carry both; clients show the email when there is no name, and the initials when there is no photo.
- **Invite:** insert invitation(pending) + outbox `invite` → Clerk `createOrganizationInvitation({role map, privateMetadata:{mwc_invitation_id, mwc_company_id}, redirectUrl: /accept-invitation, expiresInDays: 14})`. Honor Clerk's 250/h limit and `Retry-After`. *Built in S1.7* (`apps/server/src/modules/members/`): admins and owners invite (an admin never an owner); a member's email is 409 `already_member`, a pending invitation's 409 `invitation_pending`; resend moves the expiry to 14 days from now and has the outbox revoke the provider's copy and send a new one with the same metadata; revoke is local first, then `revoke_invite`. The `invite` handler finds the provider's copies by `mwc_invitation_id` before sending, so a retry never sends a second email; a provider refusal that no retry fixes (`invalid`, such as an organization's member limit) fails the row at once with the provider's message and the invitation `failed`. Our `expires_at` is the authority: a pending invitation past it counts as expired everywhere (`invitationStatusAt`).
- **Accept:** three paths funnel into one idempotent projector: webhook `organizationMembership.created` / `organizationInvitation.accepted`; reconcile-on-sign-in of the invitee; periodic reconcile (10 min per company) + manual "Sync now". Link by `mwc_invitation_id` metadata or the external invitation id, never by email. Role comes from our invitation row. Inbound Clerk role changes map `org:admin`→admin (never auto-owner); our DB wins on conflict. *Built in S1.7*: `projectIdentityEvent` (the webhook path S1.8 calls), `GET /api/me` (sign-in), `reconcileCompany` and `POST /api/companies/:companyId/sync` (the periodic path S1.10 schedules, and Sync now), in `apps/server/src/modules/identity/`. An acceptance of an invitation revoked, expired or failed here activates nobody, and the provider membership is queued for removal (`remove_member` by subject); a revoke that crossed the acceptance ends the same way. The revocation of a copy a resend replaced is not about our invitation and is ignored. *S1.12*: `POST /api/me/reconcile` runs the sign-in reconcile again on the person's request (once per person every 10 s per process), so a person already signed in sees an invitation they accepted at once (the web's `/accept-invitation` calls it); every path writes the acceptance's audit rows by the system, with the request's id (the delivery id for a webhook, none for the periodic reconcile).
- **Role change / remove / delete:** local first (access ends immediately), then the outbox op to Clerk; last-owner guard; removal re-parents direct reports and revokes the person's API keys; company delete is soft (`status=deleted`, name confirmation); hard purge is a later job. *Built in S1.6* (`apps/server/src/modules/members/`): `GET/PATCH/DELETE /api/companies/:companyId/members[/:membershipId]`; an owner gives any role, an admin moves people among admin, member and viewer but never touches or makes an owner, members and viewers change nothing, anyone may leave; each change runs under the company row's lock and re-reads the acting member there, so the last-owner guard (409 `last_owner`) holds under concurrency; a role change sets both `role` and `granted_role` (an inbound `org:admin` raises `role` again only with a newer provider state); a removal sets `status=removed`, revokes the person's API keys in the company and audits each; the `update_role` and `remove_member` handlers push the membership's state when they run, so retries and out-of-order rows converge, and wait while the company has no organization yet. *Built in S2.4*: the removal also takes the person off the org chart in the same transaction, their direct reports moved up with `reparentOnRemoval` (falling back on the earliest other active owner), audited by the member who removed them; a removal at the provider (a webhook, a reconcile, a deleted user) or a suspension does the same, by the system (docs/roadmap.md, S2.4).
- **Multi-company:** `GET /api/me` → user + memberships; the active company is the URL `/:slug` (a company's slug is never one of the app's own first path segments: `RESERVED_SLUGS` in `@mwc/shared/slugs`, refused by the API with 422 `slug_reserved` and skipped by derived slugs; old `/c/<slug>/...` links are replaced by `/<slug>/...`); the web also calls Clerk `setActive` so Clerk components stay coherent; Clerk "Personal accounts" stays enabled so `sts=pending` never blocks. *Built in S1.11* (`apps/web`; `docs/clerk-setup.md`, "The web app"): the web boots from `GET /api/config` (public, never a secret: `identity`, Clerk's publishable key with `clerk` only, `webOrigin`, `apiUrl`), so one image runs anywhere and the key is never built in; `@clerk/react` with telemetry off and Clerk's navigation through the web's own small router; `/sign-in`, `/sign-up`, `/accept-invitation` (the ticket's sign-up or sign-in, then the company of the newest Clerk membership once `GET /api/me` lists it); `/` opens the last company used in this browser (its slug in `localStorage`), else the first, else onboarding (`/companies/new`); the company shell `/:slug` calls `setActive({ organization })` with the company's `identityOrgId` (now in `GET /api/me`'s memberships), ignoring refusals, and polls `GET /api/me` while the company is provisioning; every API call sends `Authorization: Bearer <getToken()>`. The members, API keys and settings pages offer only what the server allows (`grantableRoles` and `mayRemove` of `@mwc/shared/roles`, held to the members rules by tests) and show its refusals in plain words; a key's secret lives only in the page's memory. `MWC_IDENTITY` defaults to `clerk` only for a well-formed `CLERK_SECRET_KEY` (a placeholder leaves sign-in off, with a warning naming the variable).
- **Service auth:** `api_keys` secrets `mwc_<pk|rk|sc>_<base62×32>` shown once, SHA-256 stored; personal keys expire ≤ 365 days (default 90); runner keys bound to a machine; **run tokens** are server-signed EdDSA JWTs `{typ:'run', cid, rid, aid, exp}` (1 h sliding, revoked by run state). `authn()` yields `Actor{kind user|agent|runner|system, via clerk|api_key|run_token}`. *Built in S1.4:* `secret_hash` is the SHA-256 of the whole key; personal keys act as their principal's user in their own company only (`Actor.companyId`), `last_used_at` is written at most once a minute; runner and SCIM keys and run tokens are refused until their stages (S3, later, S4). *Built in S1.9* (`apps/server/src/modules/api-keys/`): `POST /api/companies/:companyId/api-keys {name, expiresInDays?}` makes a personal key for the caller (any active member, signed in with a session only: an API key never mints keys, 403), 32 base62 characters from the CSPRNG without modulo bias (`generateApiKey` in `platform/auth/api-keys.ts`), the SHA-256 and the display prefix (`mwc_pk_` and 4 characters) stored, the whole key in the 201 response only (`cache-control: no-store`), never logged or audited; it runs under the company's lock with the membership read again, so a concurrent removal either revokes the new key or refuses it. Scopes are stored empty, meaning full access as that member in that company (finer scopes are later). `GET .../api-keys` lists my keys (status as of now: active, expired, revoked; last use), `?all=1` every personal key with its owner for admins and owners; `DELETE .../api-keys/:keyId` revokes (own keys; admins and owners anyone's), a key revoked already is a 200 no-op, another company's key a 404. The key format lives in `@mwc/shared/api-keys`, shared with the CLI. `mwc login --server URL --company ID|SLUG` reads the key from `MWC_API_KEY` or standard input (piped, or a hidden prompt; never an argument), checks it with `GET /api/me` and its company, and saves `{server, companyId, companySlug, key}` per server in `~/.config/mwc/credentials.json` (0600, folder 0700, written atomically; `MWC_CONFIG_DIR` moves it); `mwc whoami` prints user, company, role and key prefix (`MWC_SERVER` + `MWC_API_KEY` take precedence over the file); `mwc logout` removes a server's login. The file helpers are `@mwc/cli/credentials`, which `@mwc/mcp` (S2.6) reuses.
- **Personal routes and subscriptions:** *built in S3.1.* A route under `/api/me/...` whose rows are the caller's own and no company's uses `personalRoute(deps, { path, tag })` (`apps/server/src/platform/auth/personal.ts`): `authn()`, then `requireSession()`, which lets in only a person signed in with a Clerk session and linked here and puts `c.var.userId` on the context; an API key (it acts in one company and may leak with a laptop) or a run token is 403 `session_required`, a session not linked yet 403 `user_not_linked`. The first are the subscriptions (docs/subscriptions.md): `GET /api/me/subscriptions` (the caller's, oldest first, metadata only: `id`, `kind`, `label`, `accountEmail`, `accountMeta`, `status`, `createdAt`, `updatedAt`, `lastUsedAt`), `POST` (a pasted kind with a `label` and its secret: a setup-token starting `sk-ant-oat01-`, an Anthropic key `sk-ant-api`, an OpenAI key `sk-`, or a gateway's http(s) `baseUrl` with 1 to 20 `headers`; format checks only, no provider call; 201 with metadata), `PATCH /:credentialId` (`label`) and `DELETE /:credentialId` (204; the audit rows and uses stay). Another person's subscription, an unknown one and a malformed id are the same 404 `credential_not_found`. No answer, audit row or log line carries a secret: answers are built from metadata, audit rows record kind, label, account, status and owner, and the logger blanks secret keys (`REDACTED_PATHS` in `platform/logger.ts`). The master key is `MWC_MASTER_KEY` (required in production), in development `.data/master.key`, made once (0600) and never overwritten, with NODE_ENV=test a key in memory (`platform/secrets/master-key.ts`); `platform/start.ts` loads it before opening the database. *S3.3:* `GET /api/me/subscriptions/limits` gives each subscription's live 5-hour and weekly windows from its provider (the usage API for the two logins, a one-token Messages request's rate-limit headers for a setup-token, none for keys and gateways), refreshing a login's expiring token and sealing the new one again, from an in-memory cache with a 5-minute floor (15 for the probe); details in docs/subscriptions.md, "The limits API".
- **Webhooks in dev:** reconcile is the default and webhooks are optional. For the real two-user test, run `ngrok http 9950` once and point the Clerk dev endpoint at `/api/webhooks/clerk` (raw body → `verifyWebhook` → `identity_events` deduped on svix id → process; `data.updated_at` guards ordering; never recreate a deleted object). *Built in S1.8* (`apps/server/src/modules/identity/`; setup in `docs/clerk-setup.md`, "Webhooks"): no bearer, the body read raw and capped at 512 KB (413); without `CLERK_WEBHOOK_SIGNING_SECRET` the route answers 503 `webhooks_not_configured`; a bad or missing signature, a timestamp more than 5 minutes off or a signed body that is not an event is a 400 that records nothing; a verified delivery is inserted `on conflict do nothing` on `(provider, svix id)`, so a replay is a 200 that does nothing; it is projected at once in one transaction with its audit rows (by the system, the svix id as the request id); a processing failure is a 200 with the row `failed` and its backoff, which `retryIdentityEvents` (scheduled by the jobs loop, S1.10) retries under `for update skip locked` and gives up after 12 tries, as the outbox does; an event type nobody projects is recorded as `ignored`. The projector's marks keep a deleted user, membership or company from coming back (tested through the route).
- **Jobs loop:** *built in S1.10* (`apps/server/src/platform/jobs/`, started by `platform/start.ts` when `MWC_JOBS` is on: the default, off with `NODE_ENV=test`, on in the prod-like compose stack). One process per database runs it: it holds a Postgres session-level advisory lock, `pg_try_advisory_lock(0x6d7763, 1)`, on a connection reserved from its pool (`reserveSession`), so the lock ends with that session when the process dies or its connection breaks; the other processes try again every 30 s, and a holder checks the lock (`pg_locks` of its own backend) before each tick. PGlite has advisory locks and runs the same code, but one PGlite database is one session, so it cannot exclude a second holder in the same process; a PGlite database belongs to one process anyway. A tick runs every 5 s, one timer at a time (ticks never overlap): the identity outbox (up to 20 due rows claimed with a 5-minute lease under `for update skip locked`, run in enqueue order with the handler of their op from one registry that `app.ts` composes from the modules' maps; an op with no handler fails the row at once), then `retryIdentityEvents`, then the periodic reconcile: every active company with an organization about once per `MWC_RECONCILE_MINUTES` (default 10), each in its own slot (its offset in the interval is the last 32 bits of its id, random in a UUID v7), at most 10 a tick, never reconciled or longest waiting first; `companies.reconciled_at` records each run, a provider failure included (logged; the company comes round again in its next slot, not on every tick), and a company deleted meanwhile is skipped. Each job's failure is logged and never reaches the server; without a provider (`MWC_IDENTITY=none`) the ticks idle after one log line and the outbox rows wait untouched. Graceful shutdown stops the loop with the HTTP server, waits up to 5 s for the tick in flight, gives the lock up, then closes the database. `/readyz` shows a `jobs` block (enabled, this process holds the lock, the last tick, the outbox rows due and failed), which never makes it fail. Nothing lives in memory: the rows say what is due after any restart. Waking the loop early with `NOTIFY` on enqueue is left for later (a tick is at most 5 s away).
- **`IdentityProvider`** (`packages/identity-core`): `verifyAccessToken`, `getUser`, `listUserOrganizations`, `createOrganization`, `findOrganizationByMetadata`, `deleteOrganization`, `listOrganizationMembers`, `updateMemberRole`, `removeMember`, `createInvitation`, `revokeInvitation`, `listInvitations`, `parseWebhook` → normalized events (`user.upserted|deleted`, `org.upserted|deleted`, `membership.upserted|deleted`, `invitation.accepted|revoked`; any other verified type as an `ignored` event with its delivery id, S1.8), plus `capabilities{organizations, invitations, webhooks, scim}`. A future `OidcScimProvider` verifies any issuer's JWKS with `jose`, keeps companies local, and exposes SCIM 2.0 routes (`/scim/v2/Users|Groups|ServiceProviderConfig|Schemas|ResourceTypes`, bearer = `api_keys.kind='scim'` per company) whose writes become the same normalized events (attribute map: `userName`→email, `externalId`→subject, `active`→status, Groups→roles). Clerk's own Directory Sync (inbound SCIM from Okta/Entra, GA 2026-04-16, self-serve since 2026-09-30; billing may change 2027-01-01) covers most enterprise IdPs with no code from us.

## 8. Runner protocol v1 (`@mwc/shared/runner-protocol.ts`, doc `docs/runner-protocol.md`)

- **Transport:** one outbound WebSocket per runner, `GET /api/runner/ws`, subprotocol `mwc-runner.v1`, JSON frames validated by zod on both sides (max 256 KB; event batches ≤ 100 events / 64 KB; ping/pong every 20 s). WS over long-poll because the server must push answers, mid-turn input and stops with low latency; over gRPC because bidi streams and a proto toolchain buy nothing in a zod monorepo and WS passes IAP/NAT/ingress unchanged.
- **Enrollment and auth (Buildkite-style tiers):** `POST /api/machines/enrollment-tokens` (UI/CLI) → `mwc runner install --server URL --token mwc_et_…` → `POST /api/runner/enroll {name, os, arch, hostname, unix_user, claude_version}` → `{machine_id, runner_key mwc_rk_…}` (0600 on the machine; sha256 in `api_keys`). `key.rotate` rotates it with a 10-minute overlap. Each run gets its own run token for MCP/API callbacks.
- **Runner → server:** `runner.hello{protocol:1, version, caps{harnesses, slots}}` · `runner.heartbeat{awake_ms, load1, live_runs[], backlog, now}` every 20 s (= lease renewal) · `runner.resync{runs[{run_id, state running|exited|gone, exit_code, last_seq}]}` on every (re)connect · `job.accept|job.decline{id, run_id, reason}` · `run.events{events[{run_id, seq, at, kind, data}]}` · `attention.create{id, run_id, kind, wait live|next_turn, prompt, options}` · `cmd.ack{cmd_id, ok, error}`.
- **Server → runner:** `server.hello{protocol, min_runner_version, update?{version,url,sha256,sig}}` · `job.offer{id, run_id, agent_id, expires_at}` · `run.start{cmd_id, spec}` (spec: ids, harness, placement{home, config_dir, worktree}, session{mode new|resume, session_id}, model, effort, permission_policy, system_prompt, inputs[], secrets (env only, never journaled), run_token, limits) · `run.input{cmd_id, run_id, input_id, text}` · `attention.resolved{cmd_id, run_id, attention_id, answer, by}` · `run.stop{cmd_id, run_id, mode graceful|kill}` · `run.ack{run_id, acked_seq}` · `key.rotate` · `runner.drain`.
- **Semantics:** events carry `(run_id, seq)` assigned at journal-append time; the server inserts `ON CONFLICT DO NOTHING` and acks the highest contiguous seq; commands carry `cmd_id` and are acked; duplicates after reconnect are normal. Lease `runs.lease_expires_at = now()+90 s`; lapse → run `lost` (never cancelled/failed: the v1 Mac-sleep bug), machine `offline`; on reconnect the resync reconciles `running`→running, `exited`→finalize from the journal, `gone`→`failed(runner_lost_process)` + auto re-run in the same conversation. `job.offer` expires after 30 s unaccepted and is re-offered. Backpressure: ≤ 500 unacked events in flight, then the runner stops advancing its read cursor (disk keeps everything). Unknown message types are ignored; unknown fields pass through.

## 9. Runner daemon (`apps/runner`)

- **Install:** `mwc runner install --server URL --token mwc_et_… [--name]` writes `~/.config/mwc/runner.json`, enrolls, and installs a service: macOS `~/Library/LaunchAgents/com.mwc.runner.plist` (KeepAlive, RunAtLoad, user session so the agent's OAuth works); Linux `systemd --user` unit + `loginctl enable-linger` (devbox); container: PID 1 under `tini`, no self-update. `mwc runner status|start|stop|logs|login --agent <slug>` (runs `claude auth login` under that agent's `CLAUDE_CONFIG_DIR`).
- **State dir** `~/.local/state/mwc-runner/` (`/var/lib/mwc-runner` in containers): `runner.sock` (MCP shim + health), `releases/<v>/` + `current`, `agents/<slug>/claude` (per-agent `CLAUDE_CONFIG_DIR` when the server does not name one), `runs/<run_id>/{spec.json (secrets stripped), token, mcp.json, settings.json, system-prompt.md, in.ndjson, in.fifo, feeder.pid, pid, pgid, exit, out.ndjson, err.log, events.ndjson, cursor.json, commands.ndjson}`.
- **Detached spawn (v1's trick, now local):** `setsid sh -c '{ tail -c +1 -f in.ndjson > in.fifo & echo $! > feeder.pid; }; exec "$@" < in.fifo > out.ndjson 2> err.log; echo $? > exit.tmp && mv exit.tmp exit'` with `MWC_RUN_ID` in env; Node `spawn({detached:true}).unref()`. The feeder, not the runner, holds the fifo open, so a runner restart cannot EOF Claude's stdin. **Re-attach** at boot: for each run without `exit`, check `pgid` alive and `MWC_RUN_ID` in the process env; attached → tail `out.ndjson` from `cursor.out_offset`; gone → report `gone`. Each parsed line becomes normalized events appended to `events.ndjson` (the outbox, fsync per batch) then sent; `run.ack` advances `acked_seq`; `events.ndjson` of finished runs is deleted after ack, `out.ndjson` after 7 days.
- **Health :9953** (`{connected, live_runs, backlog, version}`). **Server down:** runs continue, journal grows, inputs queue server-side in `run_inputs`; reconnect backoff 1→60 s with jitter, never gives up. **Mac sleep:** awake time via monotonic deltas; a heartbeat gap > 2× interval triggers an immediate resync. **Self-update:** `server.hello.update` → download to `releases/<v>/`, verify sha256 + Ed25519 signature (baked-in public key), flip `current`, exit 75 when idle (the service manager restarts it); `runner.drain` stops accepting offers first. **Stop ladder:** SIGINT (ends the turn with a `result`), 20 s, SIGTERM (exit 143), 10 s, SIGKILL the pgid; the `exit` file is the proof; the server marks `stopped` only after the exit event or a `gone` resync.
- Mac note: Kandji bills every process start, so the runner spawns one Claude process and one MCP shim per run, never a process per tool call, and keeps PATH short.

## 12. Server-side run model (`apps/server/src/modules/{machines,tasks,runs,inbox}`)

- **State machine:** `queued → offered → starting → running ⇄ lost → completed | failed | stopped`; `waiting_on ∈ {null, permission, question}` is a sub-state of `running`; a partial unique index enforces one live run per task.
- **Wake:** `POST /api/tasks/:id/messages` by anyone but the assignee agent → a live `running` run gets `run_inputs(message)` + `run.input`; `queued/offered` → nothing (start delivers all undelivered inputs in order); none → insert `queued`.
- **Scheduler** (`LISTEN mwc_queue` + 5 s tick, `FOR UPDATE SKIP LOCKED`): pick a placement on a connected machine with a free slot and agent concurrency → `job.offer`; `starting` on `job.accept`; `running` on the first event. **Reaper** (30 s): expired lease → `lost`; `offered` > 30 s → `queued`; `lost` > 24 h → `failed(runner_lost)` with one-click re-run; permission items > 15 min → `expired` + deny. Nothing lives in memory: after a server restart, schedulers and reapers rebuild from rows and the next `runner.resync`.
- **SSE:** `GET /api/tasks/:id/stream`, `GET /api/inbox/stream` emit `run_event|message|attention|run_status` with `id` = row ids, honor `Last-Event-ID`, fed by `NOTIFY`.
- **Endpoints:** `POST /api/runner/enroll`, `GET /api/runner/ws`; `GET/POST /api/machines`, `POST /api/machines/enrollment-tokens`, `POST /api/machines/:id/drain`; `GET/POST /api/agents/:id/placements`; `GET/POST /api/tasks`, `GET/POST /api/tasks/:id/messages`, `GET /api/tasks/:id/stream`, `GET /api/tasks/:id/runs`, `POST /api/runs/:id/stop`, `GET /api/runs/:id/events?after=`; `GET /api/inbox`, `POST /api/inbox/:id/answer {option_ids?|text?|decision?}`, `POST /api/inbox/:id/dismiss`; `GET/POST /api/credentials` (S6). All under `/api/companies/:companyId/…` where tenant-scoped.
- **UI minimum:** task thread with inline run events and status; inbox with option buttons / text / allow-deny; machines page (online, slots, versions, live runs); org chart; members.

## 13. Container stack (`deploy/compose.yml`)

As built in S0.5 (the server runs the jobs loop since S1.10, `MWC_JOBS: "on"`): `deploy/compose.yml` (project `mwc-v2`) holds only the dev Postgres on 9952 that `mwc dev` and the `mwc check --full` Postgres lane use; the prod-like stack is `deploy/compose.prod.yml` (project `mwc-v2-prod`: `postgres` on 9992, the one-shot `migrate` running `node packages/db/scripts/migrate.ts`, `server` on 9990 serving `apps/web/dist`), built from `deploy/Dockerfile.server`, which runs the TypeScript sources on Node 24 directly (no tsx, no server build). `runner-local` joins in S3. The plan as approved:

Services: `postgres` (17, :9952, volume) · `migrate` (one-shot `pnpm --filter @mwc/db migrate`; `server` has `depends_on: migrate: service_completed_successfully`) · `server` (:9950, serves `apps/web/dist`, `/healthz` `/readyz`) · `runner-local` (image `mwc/runner`: node 24 + pinned `claude` + git + gh; volumes `work:/work`, `runner-state:/var/lib/mwc-runner`; tmpfs `/run/mwc` for token files; `stop_grace_period: 90s`; healthcheck on :9953) · `web` only in dev (:9951). ## 18. Risks and mitigations

| Risk                                                                             | Mitigation                                                                                                                                                  |
| -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Claude Code flag/event changes (fast cadence; `-p` Manual default since 2.1.302) | pin the CLI per machine (`claude install <v>`, version in `machines`); fixtures per version; feature detection from `system/init`; a nightly real-CLI smoke |
| Invitation metadata not copied / Clerk instance settings                         | link by external invitation id too; the real-Clerk contract test in S1.2 before any UI; `docs/clerk-setup.md` checklist                                     |
| Webhook duplicates / out of order                                                | svix-id unique, `updated_at` guard, soft deletes, one projector for all paths                                                                               |
| Token expiry or auth failure mid-run                                             | `api_retry` auth errors → `failed` attention item; setup-token rotation reminder 30 days ahead                                                              |
| Runner under a different unix user than the agent home                           | `agent_placements.unix_user` checked at `run.start`; decline with a reason                                                                                  |
| Laptop asleep / devbox stopped                                                   | lease lapse → `lost`, never cancelled; 24 h grace; resync reconciles; `gone` → auto re-run in the same conversation                                         |
| Journal growth / disk                                                            | 16 KB tool-result cap; delete after ack / 7 days; `max_turn_s` and `--max-budget-usd` limits                                                                |
| PGlite ≠ Postgres                                                                | `mwc check --full` on compose Postgres; no extensions                                                                                                       |
| Tenant leak through a raw handle                                                 | composite FKs, restricted import, OpenAPI-driven cross-tenant fuzz                                                                                          |
| Permission tool contract shape (assumed)                                         | recorded in S4.1 with the installed CLI before S5 starts                                                                                                    |
| Mac process-start cost (Kandji)                                                  | one Claude process + one shim per run; short PATH in the service env                                                                                        |
| Version churn (Drizzle, zod 4, hono-openapi)                                     | pin exact versions in S0; upgrades are their own tickets                                                                                                    |
